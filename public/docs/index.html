GETTING STARTED

Investigate the change, not just the event.

Watchtower is a read-only historical investigation system for three configured Base contract profiles. It turns one approved proxy upgrade event into a bounded evidence path: verify the trigger, run exact-block checks, let a tightly constrained agent choose approved follow-ups on configured live scans, derive the result deterministically, and issue a receipt.

CURRENT BOUNDARY

The public MVP does not accept arbitrary addresses, event signatures, calls, RPC URLs, or block ranges outside the registered profile. A replay is always labeled as a replay.

01OBSERVE

Verify the configured event and historical trigger evidence.

02PLAN

Select the immutable registered investigation plan.

03CHECK

Run initial deterministic historical checks.

04INVESTIGATE

Let the bounded agent request only approved follow-up check IDs.

05DECIDE

Derive severity and disposition with deterministic rules.

06VERIFY

Issue and browser-verify the canonical receipt.

QUICK START

Follow one evidence path.

The current app is a focused demo of registered historical investigations. It is designed to be inspected without a wallet.

  1. 01

    Choose a registered profile

    Select Aave V3 Base Pool, Compound III Base USDC Comet, or ether.fi Base weETH OFT.

  2. 02

    Replay or scan

    Replay one committed fixture immediately. The server-selected ether.fi profile can run the bounded live scan when its archive RPC is available.

  3. 03

    Read the trace

    Inspect the observed event, selected plan, exact block checks, evidence status, and final disposition.

  4. 04

    Verify the receipt

    Download the receipt or recompute its canonical SHA-256 ID in the browser.

CORE CONCEPTS

Monitoring is deliberately narrow.

Watchtower’s current registry watches one high-signal event on each configured proxy, then checks the state that gives that event context.

Signals implemented by the current profiles
SignalWhat Watchtower looks forWhy it matters
Configured proxy upgradeUpgraded(address) from the profile’s primary proxy at its approved block.Creates a precise implementation-change trigger for investigation.
Historical implementation stateEIP-1967 implementation storage at block N−1 and block N.Shows whether the proxy state agrees with the decoded implementation.
Implementation bytecodeDeployed code presence and configured byte length at the upgrade block.Confirms that code exists at the implementation address being checked.
Protocol identityFixed profile calls such as Aave `getPool()`, Compound `governor()`, or ether.fi `endpoint()`.Checks that the configured protocol identity still matches its approved assertion.

Ownership changes, pause events, transfers, treasury activity, liquidity changes, wallet movements, and dynamic project discovery are outside this MVP.

INCIDENTS

An incident is a verified signal with context.

Watchtower does not turn every transaction into an alert. A current incident is created when the configured proxy emits the approved upgrade event. The alert carries a factual title and summary, severity rule, observation time, evidence status, source links, and the associated investigation.

INVESTIGATIONS

Every alert follows a fixed trace.

After a candidate log is found, the scanner validates its block, transaction, and receipt, strictly decodes the event, selects a registered versioned plan, and executes only the checks authorized for that profile. On a configured live ether.fi scan, the agent can choose which remaining registered check to inspect next.

  1. 01
    Observe

    Confirm the configured emitter, topic, block, transaction, receipt, and decoded implementation.

  2. 02
    Plan

    Choose the approved, escalation, or incomplete plan from the closed registry.

  3. 03
    Check

    Read implementation state at N−1 and N and verify bytecode at N.

  4. 04
    Investigate

    The bounded agent may select remaining check IDs; deterministic code supplies and executes their fixed parameters.

  5. 05
    Decide

    Deterministic rules derive the disposition after every required plan check has run.

  6. 06
    Verify

    Bind the trigger, plan, checks, limitations, links, and disposition into canonical JSON.

DETERMINISTIC VERDICT PATH

The model can choose only the order of approved follow-up check IDs. It cannot supply RPC parameters, change severity or disposition, or modify receipt v1. Missing credentials and provider failures are visible while deterministic checks continue.

SYSTEM

From Base evidence to a readable result.

01BASE

Provides the historical block, transaction, receipt, and log data.

02VALIDATED INGESTION

The ChainReader boundary validates the shape and identity of RPC responses.

03DETECTION

The scanner filters one configured proxy and one approved event topic.

04BOUNDED AGENT

On configured live ether.fi scans, OpenRouter returns strictly validated decisions selecting only registered check IDs.

05EVIDENCE / RECEIPT

Assertions, limitations, links, and disposition are normalized into records.

06WATCHTOWER UI

The static workspace renders the archive, trace, failures, and verification actions.

ARCHITECTURE

A small system with explicit boundaries.

01

Frontend

Vanilla HTML, CSS, and browser JavaScript served from public/. It renders the profile archive and investigation workspace.

02

Express API

Express exposes health, configuration, bounded scans, in-memory alerts, and validated receipt downloads.

03

Base RPC reader

viem provides read-only JSON-RPC access. The RPC URL stays server-side.

04

Rules and bounded agent

TypeScript selects a registered plan and executes fixed checks. An optional server-side OpenRouter adapter can choose follow-up check order but cannot control RPC parameters or outcomes.

05

Storage

Scan results, alerts, evidence, and live receipts are held in process memory. Committed fixture data powers the public archive.

06

External links

Recorded explorer links point to BaseScan. There is no notification service, worker, database, authentication layer, or wallet integration.

LIMITATIONS

Know what the evidence does not say.

IMPORTANT

Watchtower monitors configured deployed systems for observable upgrade evidence. It is not a smart-contract audit and does not guarantee that a contract is safe.

  • Scope. Only three Base profiles and the configured Upgraded(address) event are supported.
  • Historical access. Exact-block checks need an archive-capable provider. RPC outages, timeouts, rate limits, or pruned history can produce incomplete evidence.
  • Agent availability. Live agent decisions require server-side OpenRouter credentials. Missing credentials or provider failure is shown explicitly and does not stop required deterministic checks.
  • Live coverage. The live API scans one server-selected profile and one approved historical range. Other profiles are verified fixture replays.
  • Persistence. Live alerts and receipts are in memory and disappear when the process restarts.
  • Interpretation. Receipts do not establish identity, intent, causality, governance legitimacy, implementation safety, or remote cross-chain safety.
  • Out of scope. There is no continuous monitoring, notification delivery, authentication, wallet access, transaction submission, database, multi-chain support, dynamic proxy discovery, or arbitrary RPC execution.

REFERENCE

Frequently asked questions.

Can Watchtower prevent an exploit?

No. It reports observable evidence after a configured event and does not prevent transactions or replace a smart-contract audit.

What are receipts?

Canonical JSON records whose SHA-256 IDs can be recomputed in the browser. They include the trigger, plan, checks, errors, limitations, disposition, and sources.

How quickly are changes detected?

There is no continuous monitoring or latency promise. The current live path is a bounded scan initiated by the user.

Can I monitor multiple contracts?

The registry contains three predefined profiles. The current MVP does not accept arbitrary contracts or open-ended project graphs.
